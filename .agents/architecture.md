# Architecture

Goal: a tile-based Android launcher. A tile is **data** (what it is, how big, what colour, what it opens); a source fills it with current content; the grid draws it. Adding a tile kind must be additive — a new kind and its view, nothing else.

Only the files marked *planned* below are still to be written; the rest exist. Keep this list in step with `lib/` as phases land.

## Rules
1. **`model/` imports no Flutter and no platform code.** It depends on `services/` only through abstract interfaces passed in (constructor injection). This is what makes it fully unit-testable.
2. **A tile is data plus a view.** `Tile` says what it is, how big, what colour and what it opens. It never holds a widget, a `BuildContext` or a live subscription.
3. **Content is a value, not a side effect.** A `TileSource` yields `TileContent`; the grid renders whatever the latest value is. Sources never touch the UI and never launch anything.
4. **Packing is pure.** Turning an ordered list of tiles into rows of the 4-column grid happens in `model/tile_layout.dart` and is unit-tested. Widgets lay out what they are given.
5. **Platform access goes through `AppRepository`.** Fake it in tests. Swapping the underlying package/channel must touch exactly one file.
6. **Dependency injection by constructor**; wire everything in `main.dart`. No service locators or singletons/globals.
7. **Widgets only render state and forward taps.** No matching, packing or app-launching in widgets.
8. Cache the installed-app list in the repository (with an explicit refresh); don't re-query the OS on every keystroke.
9. **Colour comes from `ui/theme.dart` only.** Sixteen VIC-II colours, nothing mixed, nothing interpolated.

## Adding a tile kind
1. A value in `TileKind`, and if it has a launch target update `launchTargetOf`; a case in `TileContent` if it has live content at all (a kind can have none — an app tile doesn't).
2. If it's a live tile, a `TileSource` for it (`services/`, behind the abstract interface, with a fake in `test/fakes/`); wrap it in a `TilePoller` at whatever interval suits it.
3. A content view in `ui/`, wired into the `tileContent(tile, {labelFor})` dispatcher in `tile_view.dart` — the one place that switches on kind.
4. If it can be pinned by the user (not every kind has to be — nothing stops a future kind that's always present), add a `PinnedTile` factory for it and a case in `GridState`/`add_tile_sheet.dart`.
5. Unit tests for the source and the content shape; a widget test for the view at each size it supports.
No changes to `TileGrid`, `EditableTileGrid`, `packTiles` or `HomeShell` should be needed — they all dispatch through `tileContent`/`launchTargetOf`/`PinnedTile`, never on `kind` directly. If a change there turns out to be needed, the abstraction is leaking; fix that first.

## The look
The reference is `design/reference/`: the C64 screen (light blue on blue), beige-and-brown hardware, the rainbow stripe, chunky bevels, pixel type.
- Hard edges. `TileMetrics.radius` is 0 and stays 0 unless the user asks otherwise.
- Depth is a bevel, never a blurred shadow or gradient: on a tile 3px light on the top and left and a thicker 5px dark on the bottom and right (`TileMetrics.tileBevelLight` / `tileBevelDark`, mitred at the corners); 2px (`TileMetrics.bevel`) everywhere else (keys, frames). The extra touches on a tile (`TileGloss`) are flat, square-edged shapes too.
- `design/mockups/` is **structure only** — which screens exist and what is on them. Its acrylic frost, 12px radii, Inter type and Fluent palette are explicitly not the target; `design/mockups/DESIGN.md` is read for layout and component inventory, not for styling.

## Decisions log
Record decisions that future agents can't derive from code (append, newest last):
- State management: plain `ChangeNotifier`; no package. (Revisit only if multiple screens/shared async state appear.)
- App access will be hidden behind `AppRepository` because `device_apps` is discontinued; a small `MethodChannel` in `MainActivity.kt` is preferred over a package.
- Palette is limited to the sixteen VIC-II colours (Pepto calibration) in `ui/theme.dart`. The limit is the design: a tile picks a colour from the sixteen or it does not get one.
- The launch window colour (`android/app/src/main/res/values/colors.xml`, `launch_canvas`) duplicates `TileColors.canvas` so the launcher never flashes a different colour on start. Change both together.
- Launch theme is `Theme.Black.NoTitleBar` in both `values/` and `values-night/`: the launcher's look does not follow the OS dark-mode setting.
- Pixel font: **Press Start 2P** (OFL 1.1), bundled at `fonts/PressStart2P-Regular.ttf` with `fonts/OFL.txt`, named by the single constant `kPixelFontFamily` in `ui/theme.dart`. A C64 face (`C64 Pro Mono`) was rejected: it is free for non-commercial use, but its licence separately forbids "provid[ing] the font for direct download from any web site," which a public GitHub repo does via raw file URLs regardless of the app's own licence. Revisit only if the repo becomes private.
- `AndroidAppRepository`'s `MethodChannel` and `GridState`'s `LocalStore` are both named constructor parameters (`channel`, `store`), not `this._channel`/`this._store`: an initializing formal would make the parameter name the private field name, which a test file (a different library) cannot pass by name. The `prefer_initializing_formals` lint is silenced at each for this reason — the pattern repeats whenever a class takes a swappable collaborator by name.
- `uninstall`/`openAppDetails` were added to `AppRepository` only once the drawer's quick actions (Phase 4) needed them, not ahead of time — the pattern this repo follows for every permission and interface method.
- The boot screen (`_BootScreen` in `home_shell.dart`) doubles as the app list's loading and error state, rather than being a separate splash step. It is genuinely how the launcher starts every time: apps load, then the list (later the grid) replaces it.
- Alphabetical grouping (A–Z, then Å Ä Ö) is a generic `groupByInitial<T>` in `model/alpha_grouping.dart`, keyed by a label extractor, not an app-specific function — the drawer and the contacts tile (Phase 11) call the same code, ported from the sibling terminal launcher's `terminal/tools/alphabet.dart`. The user chose Swedish order over plain A–Z when Phase 4 needed the answer.
- `packTiles` uses a skyline (per-column heightmap) algorithm, not one full-width row per tile: it tracks the next free row of each column and places each tile in the leftmost gap that lets it sit highest, so a short tile doesn't leave a hole under a taller neighbour. Chosen over simpler row-based packing because Phase 6's grid editor will mix tile sizes freely, and a real mosaic look needs tiles to interlock rather than stack one-per-row.
- `Tile` keeps a `TileKind` field with a single value (`app`) rather than dropping the discriminator until a second kind exists: the approved plan already commits to a clock (Phase 7), a device tile (Phase 8), weather (Phase 9), an agenda (Phase 10), contacts (Phase 11) and more, so the one-line cost now avoids a breaking change to every existing `Tile` call site later.
- The Phase 3 default layout (`default_tiles.dart`) gives every app a uniform `TileSize.small` — dense and uniform, not varied sizes — because there is no drawer yet (Phase 4): this grid is the only way to reach any app, so showing as many as possible densely matters more than mosaic variety. Phase 6's editor is what introduces different sizes, chosen by the user.
- A tile's bevel is two `BorderSide`s lightened/darkened from its own fill by `Color.lerp` (not a fixed light/dark grey), so every VIC-II colour gets a bevel that still reads as "the same colour, raised" rather than a generic frame.
- The home page became a curated subset once the drawer existed to reach everything else: `GridState` (a `ChangeNotifier`) holds an ordered list of pinned package names; home starts empty and grows only by pinning from the drawer. Phase 5 persisted the same list to disk (`LocalStore`) without changing its shape.
- `GridState` lives in `services/`, not `model/`, even though it holds no platform code: it's a `ChangeNotifier` (from `package:flutter/foundation.dart`), and `model/` stays free of any Flutter import so it can be unit-tested with zero widget bindings. `services/` already sets the precedent (`android_app_repository.dart` wraps a channel; `grid_state.dart` wraps a `LocalStore`, but both are shared, injected, observable state).
- `GridState.pin`/`unpin`/`toggle` mutate in-memory state and `notifyListeners()` synchronously, *then* return the `Future<void>` from saving — mirroring the sibling repo's `ThemeController.select`. A save that fails still leaves the pin in effect for this run; only the returned future throws. Callers that don't need to react to a save failure use `unawaited(...)` with a one-line reason (see `quick_actions_sheet.dart`), which the `unawaited_futures` lint otherwise flags.
- `main()` is `async` and awaits `GridState.load()` before `runApp`, rather than loading inside a widget: the saved grid is small and local, so blocking the first frame on it avoids a "nothing pinned" flash before the real layout appears. Contrast with the app list, which loads after first frame (its own `_BootScreen`/`FutureBuilder`) because a platform channel query is slower and more failure-prone than reading one `SharedPreferences` key.
- `LocalStore`/`LocalStoreException`/`SharedPreferencesLocalStore` are ported verbatim from the sibling terminal launcher (down to `InMemoryLocalStore` and the shared `localStoreContract` test suite), since the storage problem — durable JSON under a string key, values never stale — is identical.
- The drawer's search field shows a flat list ranked best-match-first (`rankApps`), not the alphabetical grouping, while there is a query: ranking and alphabetising are different orders, and grouping search hits by initial would bury the best match wherever its letter happens to sort.
- The jump index scrolls proportionally (`index / (groupCount - 1)` of `ScrollPosition.maxScrollExtent`), not `Scrollable.ensureVisible` on a per-section `GlobalKey`: the `ListView`'s sliver only builds sections near the viewport, so a distant section's `GlobalKey.currentContext` is null until it's already scrolled close — `ensureVisible` silently no-ops for exactly the far-away letters a jump index exists to reach. The `_JumpIndex` widget itself now hands back the tapped/dragged row's index (not the letter), since the letter is no longer enough to compute a scroll target.
- `_JumpIndex` (right edge of the drawer) is a `StatefulWidget`: `onTapDown`/`onVerticalDragUpdate`/`onVerticalDragStart` all route through one `_handleAt(localY)`, so a drag scrubs through every row it passes over exactly like a tap on each in turn, with a 2px bar tracking `_active` so a fast scrub still shows where the finger is.
- Tapping "Uninstall" in the quick-actions sheet calls `AppRepository.uninstall` directly, with no extra in-app confirmation: `uninstall` only ever opens Android's own uninstall dialog (`ACTION_DELETE`), which is itself the confirmation.
- `default_tiles.dart`/`tilesForApps` (Phase 3's placeholder, cycling colour by index on every render) is retired. `GridState` now stores a `PinnedTile` — id, kind, size, colour — per pinned tile; `PinnedTile.app`/`.system` run the same cycling logic exactly once, at pin time, so a tile's size/colour is a real user-changeable fact instead of being re-derived from list position on every rebuild.
- The grid editor (long-press a home tile) stages every change — reorder, resize, recolour, delete — on a local scratch `List<PinnedTile>` inside `_HomePageState`, never touching `GridState` until "Apply" calls `GridState.replaceAll`. "Cancel" just discards the scratch copy. This is what makes Apply/Cancel possible without `GridState` needing any notion of a pending transaction.
- Reordering is drag-a-tile-onto-another, not a `ReorderableListView` (which only handles linear lists): each tile is both a `Draggable<String>` (its `id`) and a `DragTarget<String>`, and dropping one onto another calls the pure `moveItem` with their scratch-list indices. `Draggable.feedback` renders in the root `Overlay`, outside this tree's `Material` ancestor, so it's wrapped in its own `Material(type: MaterialType.transparency)` — otherwise `TileView`'s `InkWell` throws "No Material widget found" the moment a drag starts.
- Long-pressing empty canvas space does *not* enter the editor, only long-pressing an existing tile does (which also selects it, matching the Stitch mockup's flow) — simpler than wiring a second gesture target, and there is nothing to edit on a grid with zero tiles anyway. Likewise, back-press does not cancel an in-progress edit (only the explicit Cancel button does): wiring that through `PopScope`, which lives two widgets up in `HomeShell`, was judged not worth it for this phase.
- `_HomePageState`'s scratch copy does not defend against `GridState` changing underneath it while editing (e.g. pinning something from the drawer via the same `PageView`, mid-edit, by swiping without applying/cancelling first). Accepted as a rare-enough edge case rather than lifting edit state up to disable `PageView` swiping.
- `Positioned`'s `key: ValueKey(tile.id)` belongs on the `Positioned` itself (the direct child of `Stack`), not nested one level down on the `TileView` inside it — only a multi-child widget's *direct* children are matched by key across rebuilds. This only started to matter once tile order could change at runtime (drag-to-reorder); `tile_grid.dart` and `editable_tile_grid.dart` both key the `Positioned`.
- Apply lives in `TileInspector`'s label row (bottom of the screen, one-handed reach), not the top `_EditorBar` with Cancel: reaching the top of a phone screen mid-edit was the user's own complaint after trying Phase 6. `TileInspector` renders unconditionally now (label blank, size/colour pickers hidden) so deleting the selected tile — which clears the selection — can never strand Apply off-screen.
- `Tile.appPackage` is gone; `Tile`/`PinnedTile` now key everything off a kind-agnostic `id` (a package name for `TileKind.app`, a fixed name like `"clock"` for a system kind — there is at most one of each, so the kind's own `.name` is a perfectly good id). `launchTargetOf(tile)` is the pure derivation of "what to launch, if anything" from `id`/`kind`; `TileGrid` only wires `onTap` when it returns non-null, so a system tile simply isn't tappable outside the editor (its `onLongPress`/select/delete/drag paths are unaffected — those always use `id`, never `launchTargetOf`).
- Device (Phase 8), needing its own platform channel, was split out of what the plan originally called "Phase 7, clock and device" — see plan.md's changelog. This phase only ever had to solve the clock, which needs no platform code at all.
- There is no auto-seeded tile: the plan's first draft would have put a clock on the grid the first time this phase ran, but the user asked for a real "add tile" entry point instead, even though it's more scope now. `add_tile_sheet.dart` lists every `TileKind` but `app` that isn't already pinned; tapping one calls `GridState.pinSystemTile`. It is deliberately generic over `TileKind`, not hard-coded to clock, so Phase 8's device tile is one more sheet entry, not a second sheet.
- `TileView` stopped taking a `Tile` + `label` and taking a `colour` + `content: Widget` instead: the chrome (fill, bevel, selection outline, delete badge) is identical for every kind, but what goes *inside* it (a glyph and a label for an app; a big numeral and a small date for a clock) is not, and hard-coding "glyph from label's first letter" into the shared shell would have made every future kind fight that assumption. `tileContent(tile, {labelFor})` in `tile_view.dart` is the one dispatch point "Adding a tile kind" asks for; `TileGrid`/`EditableTileGrid` call it and never branch on `kind` themselves.
- A live tile's ticking timer and `AppLifecycleState` observer live in a single reusable `TilePoller` widget (`ui/tile_poller.dart`), not duplicated per kind or hoisted into a `ChangeNotifier` service: it's pure widget lifecycle (mount/unmount, resumed/paused), which is a natural fit for `State`, and keeping it in `ui/` means a kind's `TileSource` stays platform-and-widget-free. `ClockTileSource` polls every 30 seconds — a home-screen clock showing minutes doesn't need per-second updates, and per-second would poll it needlessly while the screen is simply sitting there.
- `ClockTileSource` takes an injectable `now` (`DateTime Function()`, defaulting to `DateTime.now`) precisely so its tests, and `TilePoller`'s, never touch the wall clock — the same pattern `date_command.dart`'s `context.now()` uses in the sibling repo.
- `TileContent` stayed a real `sealed class` (one case, `ClockContent`, so far) rather than being deferred until a second kind existed, unlike `TileKind` earlier: a test needing a second `TileContent` for `TilePoller`'s tests would have had to fake one anyway, and `ClockContent`'s two plain strings are also exactly what `test/services/clock_tile_source_test.dart` and `test/ui/tile_poller_test.dart` reuse to avoid inventing a throwaway type.
- Sound (ringer) and flashlight tiles. The two-state kind (flashlight) uses `ToggleTileSource`/`ToggleContent`; the ringer is three-way so it has its own `SoundModeTileSource`/`SoundContent`. Both render through one `StateTileContentView` (label + a state string). `SystemControlService` has `soundMode`/`setSoundMode` plus `isOn`/`setOn(TileKind, bool)`. (First attempt modelled silent and vibrate as two independent toggles; the user corrected that — the ringer is one state that can only be normal, vibrate or silent, so one tile cycles it.)
- `TileSource.read()` became `Future<TileContent> read()` (was synchronous) specifically because the toggle kinds' state lives on the platform side and must be queried through a channel; `ClockTileSource.read()` just wraps its already-synchronous body in `async` to satisfy the interface — it does no real awaiting. `TilePoller` grew a matching `TileContent?` (was non-nullable `late`) so it can render nothing for the one frame before the first read resolves, and its `initState` fires the first read with `unawaited(...)` instead of blocking.
- `TilePoller.builder` grew a third argument, `refreshNow` — a toggle tile's own tap flips the platform state then wants to show the new value immediately, not wait up to `interval` for the next tick. Adding this to the shared widget (available to every kind, even though only the toggle kinds use it yet) was simpler than giving toggle tiles a second, near-duplicate poller.
- There is no Do Not Disturb tile (tried, removed at the user's request). Android couples DND to the ringer: `AudioManager.setRingerMode(RINGER_MODE_SILENT)` from an app is treated as "turn DND on" (alarms-only) and leaves the internal ringer at vibrate — confirmed on the user's phone, where the tile said silent while the status bar showed DND and the volume panel showed the vibrate icon, never the crossed bell. So `setSoundMode(silent)` reaches silent the way the volume rocker does: go to vibrate, then `adjustStreamVolume(STREAM_RING, ADJUST_LOWER)`. Normal and vibrate use `setRingerMode`, which has no DND side effect. There is deliberately no fallback to `setRingerMode(SILENT)` — it would reintroduce the DND side effect. The tile cycles normal → vibrate → silent → normal and shows the reported ringer mode. Unverified beyond this phone: whether `adjustStreamVolume` reaches silent on every OEM/version.
- Reaching silent (found by testing on the emulator, Android 17): the system enters silent only on a lower press that follows a press in a *different* direction (`AudioService.checkForRingerModeChange` compares against the previous direction), and remembers the last one — so a lower after an earlier lower is ignored for good, and the tile appeared to stick at vibrate. `setSoundMode(silent)` therefore does vibrate → one raise press (resets the direction; vibrate→normal) → vibrate again → one lower press. Repeating lower presses does not work. The ringer change also lands a moment after the call returns, so `tileContent`'s `_act` re-reads immediately and again 400ms later; without the second read the tile showed the old state for up to a poll interval and invited a second, wrong tap.
- `StateTileContentView` wraps its body in `SizedBox.expand`: the `GestureDetector` was only as wide as the text (loose constraints from `TileView`'s `Stack`), so a short state like `[RING]` left most of the tile dead to taps — this, not the ringer logic, was the user's "stopped reacting to touch". Any future tile content with its own tap target must fill the tile the same way.
- Entering or leaving silent needs Android's notification-policy access (`NotificationManager.isNotificationPolicyAccessGranted()`) — a special permission granted only through a Settings screen, never a runtime dialog, and not the same as declaring `ACCESS_NOTIFICATION_POLICY` in the manifest (which only lets the app ask). `SystemControlChannelHandler.withPolicyAccess` checks it (only for transitions that need it) and, if not granted, opens `ACTION_NOTIFICATION_POLICY_ACCESS_SETTINGS` instead of throwing — the same best-effort, no-error-surface contract every other platform action in this app follows. Previously pinned `silentMode`/`vibrationMode`/`doNotDisturb` tiles no longer parse (`PinnedTile.fromJson` drops unknown kinds) and vanish from the saved grid.
- The flashlight tile uses `CameraManager.setTorchMode`, not `Camera.open()`/a `CAMERA` permission: torch-only control was explicitly carved out to not need it, so the tile never triggers a runtime permission prompt. A registered `CameraManager.TorchCallback` keeps the Kotlin side's cached `torchOn` correct if the torch is toggled from outside the app (quick settings), since `setTorchMode` itself has no getter.
- `tileContent()` grew two new required-ish parameters — `systemControl: SystemControlService` and `interactive: bool = true` — the one deliberate exception to "no changes to `TileGrid`/`EditableTileGrid` needed" for a new kind: a toggle kind is the first kind whose view needs a genuinely new collaborator (not just `labelFor`), so threading it through `TileGrid`/`AppTileGrid`/`EditableTileGrid`'s constructors was unavoidable. `interactive: false` in `EditableTileGrid` stops a toggle tile's own tap zone from fighting the outer `TileView`'s tap-to-select — outside the editor (`TileGrid`, home), it defaults to `true` and the tile itself handles the tap since `launchTargetOf` is `null` for every system kind anyway.
- `TileServices` (`services/tile_services.dart`) replaces the single `systemControl` parameter that `tileContent`, `TileGrid`, `AppTileGrid`, `EditableTileGrid`, `HomeShell` and `TileLauncherApp` each carried. The device tile was the second live kind needing a platform collaborator and every later phase (weather, calendar, contacts, mail) adds another, so bundling them means a new kind's service is one field in one class plus its wiring in `main()`, not a new parameter through six widget layers. `interactive` stays a separate `tileContent` parameter: it is about the call site (editor vs home), not a service.
- `DeviceRepository.status()` never throws: a failed or missing platform query returns a `DeviceStatus` whose fields are `null`, and the view shows dashes, rather than the tile poller having an error path (`TilePoller` has none; an exception from `read()` would be an unhandled async error). Storage is the internal data partition (`StatFs` on `Environment.getDataDirectory()`) in decimal units, like Android's own storage screen. Battery comes from the sticky `ACTION_BATTERY_CHANGED` broadcast read with a null receiver, so it needs no permission and no registered receiver. The tile polls every 60 seconds (plus on resume): both change slowly.
- The device tile's two bars both fill toward "more is left" — battery by charge, storage by *free* share — because the storage label says FREE and a bar filling the other way read as "plenty" on a nearly-full disk (seen on the emulator: 648 MB free with a 90%-full bar). The bars are an outlined box filled with the tile's ink, no gradient or alpha, per the palette rule.
- Phase 9's weather code is a port of the sibling terminal launcher's (`weather.dart`, `smhi.dart`, their fixtures and tests), split to fit this repo: the value types (`Place`, `Forecast`, ...), `WeatherKind` and the WMO descriptions live in pure-Dart `model/`; `Weather`/`Smhi` and the HTTP layer stay in `services/`. Descriptions are upper case (a tile, not a card). `Weather.find` (geocoding by name) is kept and tested although no tile uses it yet: it is the natural fallback when location is refused for good, for a later settings phase.
- The tile never asks for location on its own. With no saved place it says "TAP TO USE MY LOCATION"; the tap calls `WeatherRepository.locate()`, which asks for permission, saves the place (`weather.home`, via the same `LocalStore`) and fetches. A permission dialog appearing unprompted on a home screen would be hostile, and only a tap can also be retried after a refusal. A permanent refusal has no tap action (Android would not show the dialog); the tile says where the setting is.
- `LiveWeatherRepository` keeps the last forecast in memory for 15 minutes (the `TilePoller` interval and every return to the launcher then cost nothing), falls back to it marked stale if a refresh fails, and — found on the emulator — remembers why the last `locate()` failed: the tile re-reads with `current()` straight after a tap, which otherwise reported "needs a place" again and hid every refusal or missing fix.
- Location is coarse only (`ACCESS_COARSE_LOCATION`; the system dialog offers "approximate" only). The Kotlin handler uses the network provider if enabled, else the fused provider (Android 12+); the port used the network provider alone, so a phone without one (no Play services, Google Location Accuracy off) reported "location is switched off" while it was on. GPS is never used: it needs precise location. `INTERNET` is now in the main manifest (it was only in debug/profile), which a release build needs.
- The weather tile chooses its layout from the width it is given (`_compact` 120, `_wide` 260 logical px), not from `TileSize`, so it follows the grid's cell maths and any future size: small shows the sky and temperature; medium adds the words, place and source (SMHI's licence is CC BY, so the source is always credited); wide adds five day columns. Sky pictures are 12x12 pixel-block bitmaps painted with anti-aliasing off (hairline seams otherwise), not the sibling's anti-aliased line drawings, to keep the hard-edged look.
- Testing location on the emulator needs a mock provider: the emulator's `geo fix` feeds only GPS, which a coarse-only app cannot use, so the fused provider returns "no location fix". `adb -s emulator-5554 shell appops set com.android.shell android:mock_location allow`, then `cmd location providers add-test-provider network`, `set-test-provider-enabled network true`, `set-test-provider-location network --location 57.70,11.97 --accuracy 500` (and `remove-test-provider` + `appops ... deny` afterwards) gives the app a position.
- Phase 10's calendar reading is a trimmed port of the sibling's `CalendarService`/`CalendarChannelHandler` (read only: no writable calendars, add/edit/delete, colour or description; those come with the write phase). - The "SWIPE LEFT FOR ALL APPS" hint is its own row under the tile grid, not laid over it (it was a `Positioned` in a `Stack`). - Grid editor drag, reworked after the user found it hard to use on the phone ("not possible sometimes"). Three causes, all fixed: (1) `moveItem` followed `ReorderableListView` (moving forward lands *before* the target), so dropping a tile on its next neighbour was a no-op and no tile could be dropped last by dropping on the last one; it now always puts the moved item at the target's index, i.e. swaps neighbours. (2) A grid taller than the viewport could not be scrolled while dragging, so tiles below the fold were unreachable; a held tile within 96px of the top or bottom of the scrolling area now scrolls it (a 16 ms `Timer` in `EditableTileGrid`'s state, faster the closer to the edge, cancelled on drag end and dispose). Flutter's `EdgeDraggingAutoScroller` was rejected: it only scrolls once the drag has gone *past* the viewport edge, which here is the inspector panel. (3) `Draggable` started on the first pixel of movement, so a plain finger drag over the tiles (most of the canvas) could never scroll; it is a `LongPressDraggable` (200 ms hold) now. The tile a held one is over gets a 4px yellow frame (where it will land), and the ghost is held by its centre (`dragAnchorStrategy`) so the target is the tile under the middle of the ghost. Dropping on empty canvas still does nothing; to put a tile last, drop it on the last one.
- Grid editor drop feedback changed to an insertion line at the user's request ("a line in between the destination tiles" rather than a frame that read as "replaces that tile"). The reorder is now `moveBeside(items, from, target, after)`, replacing `moveItem`: a held tile over the left half of a tile goes before it, over the right half after it, and a 6px yellow line in the gutter down that edge of the target shows which (`EditableTileGrid`, key `drop-line`; the `Stack` has `clipBehavior: Clip.none` so the line at the grid's outer edge is not cut). The order in the list is what the skyline packer lays out, so the tile lands where the packer puts it in that order, which is next to the target when there is room and on the next row otherwise. Two Flutter details found by the tests: `DragTarget.onMove` fires for *every* target under the finger, the held tile's own included (ignored by id), and the drag's `onDragUpdate` can arrive after a target's `onMove`, so the finger is derived from `details.offset` (the ghost's top-left) plus half the held tile's size (the ghost is anchored by its middle) rather than tracked separately.

Tapping the number opens a remote-style number pad (a page number starts with 1 to 8; the third digit opens the page; DEL; X puts it away) instead of the system keyboard. Underlined page numbers in a page are tappable links. A swipe left/right steps through a page's parts and then to the next/previous page, and a part bar shows `PART 2/3` with arrows. Back steps back through the pages read (a history stack), closes the number pad first, then closes the viewer (`PopScope`). Failures word themselves (TRY AGAIN reads with `fresh`), and an unbroadcast page says so while the arrows keep working.
- Alignment (the user had seen text and elements sit right of centre in the sibling's rendering): texttv.nu pages are not symmetric (headlines are indented two cells and run to the last column), so drawn as they come the text leans one way. `tvTextMargins` measures the blank cells the page's longer text rows leave at each side (ignoring the title strip, block graphics and short rows) and `tvGutters` gives the black gutter to each side that makes those margins equal; the two gutters always add to 2 cells, so the grid is the same size on every page. The trade-off is inherent: the coloured header bars run to the page's edges, so on a page that leans, the text is centred and the bar is not. Measured on the real pages 100 and 377 in a test.
- The text is Press Start 2P, monospaced (one square cell per character), fitted to the width so 40 columns plus the two gutters fill it, with a 1.6 line height for teletext proportions; block graphics are drawn by the painter. There is no zoom yet: 40 columns on a phone is small, and a text-size control would be the next thing to add if reading is hard. `flutter test` does not load the pixel font, so a rendered test image shows blocks for text (the mosaic logo is real); text layout was therefore checked by geometry in tests rather than by eye.
- The Text TV page fills the height it is given (the user saw it use about half the black area on their phone). 40 columns fix the width, so height is the free variable: `_Grid` divides the available height over the page's row units (a double-height headline row counts for two) and gives `TvRow` that `rowHeight`, at least the natural 1.6 cells and at most 3 cells (`tvCellWidth` predicts the cell width the row will pick). Backgrounds and block graphics grow with the row; the letters are stretched upright about their centre (`stretch`, up to 2x, so glyphs fill about four fifths of the row), which is how teletext looks (characters twice as tall as wide). A screen too short for the natural height keeps natural rows and the page scrolls.
- Text TV colour bars (the title banner and the navigation strip: a non-black background under 90% or more of the width, `tvIsBar`) are placed by their edges, not their words: they always get the same gutter on both sides, while the text rows get the per-page gutter that centres the text (`tvGutters`), and bar rows are left out of the text-margin measurement. Found on the phone: with everything shifted by the text's lean, the bars sat visibly off-centre. The cost is that a bar and the text rows around it start a cell apart on a page that leans, which follows the site's own layout (its bar text is right-flush).
- Air on the Text TV page (the user marked the last text line touching the bottom bar, and the bar touching the controls): the page keeps `TileMetrics.margin` of black above and below it (the rows are laid out in the height that is left), and the letters are centred in their rows and fill about two thirds of a stretched row. The centring is `leadingDistribution: TextLeadingDistribution.even` on the row's text style: with `height: 1.6` and the font's own proportional split, Press Start 2P put all the extra line height above the letters, so text sat at the bottom of its row and descenders ("g" in "säger") reached the row below.
- Phase 15's calc and convert: the expression parser (`evaluateExpression`), the unit table (`allUnits`, `convertUnits`), `formatNumber` and `CurrencyRates` (ECB rates from frankfurter.dev, six hours in the local store, kept for offline) are ported from the sibling with their tests; the pure parts live in `model/` (`expression`, `units`, `number_format`, `rates`) and only `CurrencyRates` (fetcher + store) stays in `services/`. The tile (`TileKind.calc`, id `calc`) has nothing to read from outside, so it has no poller: it opens `showCalcSheet`, a bottom sheet with CALC and CONVERT tabs and a close key (`IndexedStack`, so each tab keeps what was keyed).
- The calculator is button-based (no system keyboard): digits, `. + - * / ( )`, C, DEL and `=`, and a strip of `^ % pi e sqrt abs sin cos tan ln log exp floor ceil round asin acos atan`. All the key rules are in the pure `CalcEntry` (`press`, `backspace`, `equals`, `preview`), so the pad only draws it: a second point in a number is ignored, an operator cannot start an expression except a minus, a second operator replaces the first (a minus after `* / % ^` is a sign), `)` needs a `(` to close, functions type their bracket with them, the answer so far is shown as you key (`= 14`, brackets closed for the preview), `=` puts the answer in place of the sum, and after an answer a digit/bracket/function starts a new sum while an operator carries on. Errors are the parser's own words, in capitals, shown until the next key.
- The converter has a kind (LENGTH MASS VOLUME TIME SPEED TEMP AREA DATA, or MONEY), a FROM and a TO chip row, a number pad (`keyNumber`: 15 digits, one point, no leading zeros, `+/-`), SWAP, and the answer under the number. Each kind starts on the pair most people want (km to mi, kg to lb, C to F; SEK to EUR for money). Units convert offline (8 significant digits); money is `Rates.convert` via the euro shown in cents, with the ECB date (or `SAVED RATES ... (OFFLINE)` when the rates are a stale copy) and TRY AGAIN when there are none. Rates are only requested when MONEY is first chosen, through `RatesRepository` (never throws; `LiveRatesRepository` on `CurrencyRates`), and the usual currencies (SEK EUR USD GBP NOK DKK) come first. Chip rows are a plain `SingleChildScrollView` + `Row` (not a lazy `ListView`), so every chip exists and can be scrolled to.
- Phase 16's timers and alarms are handed to the phone's own clock app, as in the sibling: `AlarmClock` intents from the Kotlin `AlarmChannelHandler` (`ACTION_SET_TIMER` / `ACTION_SET_ALARM` with `EXTRA_SKIP_UI`, plus `ACTION_SHOW_TIMERS` / `ACTION_SHOW_ALARMS`), behind `AlarmService` / `AndroidAlarmService`. The clock app is what rings, vibrates and survives a reboot, so nothing here schedules anything, the permission is only the normal `SET_ALARM`, and the launcher can set and open but not read or cancel. The service is named `Alarm...`, not `Clock...`, because `TileKind.clock` is already the tile that shows the time; the tile is `TileKind.alarm` ('ALARM', id `alarm`). Only the pieces the pads use were ported from `clock_input.dart` (`formatDuration`, `nextOccurrence`, `clockText`, `describeDays`, `maxTimer`); the free-text parsers (`parseDuration`, `parseClockTime`, `parseDays`) belonged to the command line and are not here.
- The alarm sheet mirrors the calc sheet (bottom sheet, TIMER and ALARM tabs, close key, `IndexedStack` so each tab keeps what was keyed) and is button-based. Timer: a length keyed like a microwave (digits shift in from the right, `TimerEntry`: `130` reads `00:01:30`, `90` is a minute and a half), presets 1, 5, 10, 15, 30 min and 1 h that fill the length in (and can be added to), START, and SEE TIMERS; over 24 hours says so and cannot be started. Alarm: a time keyed left to right like a page number (`AlarmEntry`: dashes for the digits to come; a digit that could not lead to a real time is ignored, so a finished entry is always valid), day chips MON to SUN that toggle plus ONCE / MON-FRI / SAT SUN / DAILY, a `NEXT: TOMORROW 07:30` / `NEXT: MON-FRI 06:45` line, SET ALARM and SEE ALARMS. "Anything that acts asks first" is satisfied by the explicit START / SET ALARM tap; choosing a preset or a time sets nothing. A failure is worded (no clock app, not allowed).
- Not in this phase: labels on timers and alarms (the service and Kotlin handler accept one, but the pads have no text field), and reading, editing or cancelling existing ones (the clock app does that; SEE TIMERS / SEE ALARMS open its lists).
- Phase 17's settings. `LauncherSettings` is a small immutable value (theme, columns 4 or 6, gap tight/normal/relaxed, swipe down, swipe up) held by `SettingsState`, saved as one JSON blob and read tolerantly: anything unknown or out of range falls back to its default, so a settings file from a newer or older build never stops the launcher starting. `SettingsScope` (an `InheritedNotifier`) is how widgets read it; it falls back to the defaults without a scope so a widget test does not need one.
- Theme variants are palette roles, not fixed C64 colours. `TilePalette` names the roles the UI uses (canvas, bezel, text, textBright, textDim, muted, accent, highlight, danger, brightness); `TileColors.canvas` and the rest are static getters over `TileColors.current`, so the call sites did not change. Changing the theme sets `TileColors.current` and then rebuilds the whole tree by walking the element tree with `markNeedsBuild` (`_rebuildEverything` in `app.dart`) after the frame, rather than threading a palette through `BuildContext` into every widget; `MaterialApp` animates its own `ThemeData` over 200 ms (tests that change theme need `pumpAndSettle`). The tile fills stay the VIC-II colours in every variant: a theme changes the canvas and the ink, not the palette a user picked tiles from. Beige is the light one (canvas 0xFFD8CDB2, brown ink), so the status bar's overlay style follows `TilePalette.brightness` (`systemUiStyleFor`). Contrast is tested per palette: a 2.5:1 floor for the authentic C64 light-blue-on-blue, 4:1 for the two new ones.
- Grid width is the columns setting, not a constant. `TileSize.spanIn(columns)`: small 1, medium 2 (1 on a grid narrower than 2), wide and large the full width, so on 6 columns a wide tile is 6 wide. `PlacedTile` records its `span` at pack time (falling back to the size's own width) so drawing and drop targets agree with the packer; `layoutTiles`, `gridHeight` and the editor's drop line take `columns` and `gap`. The stored tile size stays `small/medium/wide/large`, so changing columns never rewrites a layout and switching back restores it.
- Export/import is text through the clipboard, not a file: there is no storage permission or file picker to add, and pasting to yourself or a chat works everywhere. `exportLayout` writes `{format: 'tile-launcher-layout', version: 1, settings, tiles}`; `parseLayout` refuses (with a reason) empty text, non-JSON, another format and a newer version, and skips (and counts) tiles it cannot read or that repeat an id. Import shows how many tiles it found and asks before it replaces the layout and the settings; CLEAR LAYOUT and RESET SETTINGS ask the same way, inline with YES / NO, not a dialog.
- The Home-app shortcut only opens Android's own page (`ACTION_HOME_SETTINGS`, then `ACTION_MANAGE_DEFAULT_APPS_SETTINGS`); Android decides what is Home, and a launcher cannot change it. Whether this launcher is Home is read by resolving the HOME intent and comparing the package, and is re-read when the app returns to the front, so choosing it shows at once. `HomeRoleService`, `ClipboardService` and `ShadeService` sit in `TileServices` though no tile uses them; the bundle is what reaches the settings screen and Home.
- Swipe gestures. Left is All Apps and is not configurable. Swipe down (at the top of Home) is one of refresh (default, the old pull-to-refresh), notification shade, quick settings, nothing; swipe up (at the bottom) is nothing (default), All Apps, or All Apps with the search field focused. `OverscrollGestures` counts overscroll from a finger (not the tail of a fling), only when the drag began with the content already at that edge, and fires once past 72 px with a haptic tick; it never consumes the notification. The `RefreshIndicator` is only built when swipe down is refresh, since it would fight for the same drag. The shade is opened with `StatusBarManager.expandNotificationsPanel` / `expandSettingsPanel` by reflection (normal `EXPAND_STATUS_BAR` permission): there is no public API, the methods are on the hidden-API greylist, and a phone or version that has removed them makes the gesture do nothing (the service answers false, nothing is shown). An empty Home page's message sits over its list and takes the touch, so a swipe that starts exactly on the message does not scroll.
- Not in this phase: blur, corner radius, 3D flip, wallpaper pass-through (the plan excludes them), a configurable swipe left, and remembering which settings section was open.
- Phase 18's press feel. `TileView` is stateful and reads the raw pointer (a `Listener`), not the tap recogniser, so a tile whose content takes the tap itself (a toggle) still sinks: while a finger is down the bevel flips (dark top-left, light bottom-right, `AnimatedContainer`, 60 ms) and the content moves down-right by the bevel width; sliding past touch slop (a scroll) lets it back up, and a selected tile keeps its outline. The pointer stream can outlive the widget (a tile being dragged in the grid editor is taken out of the tree with its pointer still down), so every callback checks `mounted`. The long-press cut-off is a `Timer`, not a `Stopwatch`, so it runs on fake time in tests.
- Haptics are one function, `haptic(context, Haptic.tap | Haptic.press)`, that reads `LauncherSettings.haptics` without depending on it (safe from an event handler). Tap ticks (`lightImpact`) on a tile whose release was a tap, and on every `PadKey`; a long-press thuds (`mediumImpact`). `InkWell.enableFeedback` is off on tiles: Material's own long-press feedback calls a bare `HapticFeedback.vibrate()`, which would ignore the setting and buzz twice. The setting is HAPTICS ON / OFF under FEEL in settings (default on).
- The boot screen is one widget with two faces. Plain (banner, memory line, READY.) is what every ordinary start shows while the app list loads. On the first run (`FirstRun`, remembered in the LocalStore once the show ends or is tapped away) `BootScreen(animate: true)` types the script out at 28 ms a character, then `LOAD "HOME",8` / `SEARCHING FOR HOME` / `LOADING` / `READY.` / `RUN` with a drawn (not glyph: the pixel font has no block) blinking cursor, and `HomeShell` holds home back until it has finished even if the apps loaded long ago. A failing app list shows the error screen at once; the same `State` object is reused for that switch, so `didUpdateWidget` stops the show, or it would finish later and mark itself seen.
- Most-used suggestions are local only. `LaunchStats` counts launches routed through `HomeShell._launch` (home tiles and the drawer; an app opened by other means is not counted), keeps at most 200 apps (the least used are forgotten first), and offers an app only after it was opened `minLaunches` (2) times, was not pinned already and is still installed. They appear under MOST USED at the top of "+ ADD TILE", tap to pin.
- The app icon is generated: `tool/make_app_icon.py` (Pillow) cuts the artwork out of `design/icon/source.jpg` by flood-filling the near-white backdrop in from the edges, then writes, for each density, an adaptive foreground (every opaque pixel within 34 dp of the centre of the 108 dp canvas, inside the 36 dp visible circle), a monochrome layer (a flat silhouette, for Android 13 themed icons), the scanline-blue background picture `design/icon/background.jpg`, and a legacy rounded-square icon; plus `design/icon/preview_circle.png`. Same approach as the sibling repo's `make_app_icon.py`.
- Project files: `LICENSE` is MIT (the bundled font keeps its own, `fonts/OFL.txt`); the README lists the features, permissions and how to build and side-load. Release builds are still signed with the debug key; that is fine for side-loading and is called out in the README.
- Phase 19's wallpapers are an action, not a setting: nothing is stored, and nothing is set on its own. SETTINGS → WALLPAPER picks a picture (one per theme, `assets/wallpapers/wallpaper_{c64,oled,beige}.png`, 1290×2870, starting on the current theme's) and a screen (LOCK SCREEN by default, HOME SCREEN, BOTH), shows the picture in a phone-shaped frame (decoded at 216 px wide, not the full picture), and SET WALLPAPER asks (YES / NO) before it does anything. DEFAULT WALLPAPER asks and then calls `WallpaperManager.clear(flags)`, which puts the phone's own wallpaper back on that screen. There is no "before" picture: reading the current wallpaper would need a storage permission on some versions, and the launcher asks for none it can do without.
- `WallpaperChannelHandler.kt` decodes the bytes on a single worker thread (a 1290×2870 bitmap is 14 MB) and replies on the main thread: `done`, `refused` (`isWallpaperSupported` / `isSetWallpaperAllowed` false, or a `SecurityException`) or `failed`. `setBitmap(bitmap, null, true, flags)` with `FLAG_LOCK` / `FLAG_SYSTEM` needs API 24; below that only the home screen can be set and a lock-screen request answers `failed`. `SET_WALLPAPER` is a normal permission, granted at install. The phone crops the picture itself (centre) to its own aspect ratio, which is why the pictures keep the top third and bottom fifth calm and the detail central.
- Tile Launcher paints its own solid canvas over whatever wallpaper there is, so a *home screen* wallpaper is only seen behind other launchers and in the app switcher; the settings screen says so beside the screen choice. Blur, transparency and letting the wallpaper show through the mosaic stay out of scope (see the plan's Phase 17 exclusions).
- The settings screen's inline question and answer now belong to a section (`_where`: layout or wallpaper) and are drawn under that section's own keys by `_feedback(where)`; before, the layout section was the only one that could ask.
- Phase 20's tile look. The bevel is asymmetric (3px lit, 5px shaded) and *pressing swaps the two widths*, so the content sinks by their difference (2px) with no separate padding shift, and the shine goes. On top of the fill, `TileGloss` draws (a) scanlines, one pixel every four at 5% black across the tile face, (b) a shine: an L of 32% white 1px inside the lit edges, up to 44px long, (c) a dithered shade: a 4px strip of 2px checkerboard squares at 20% black just inside the dark edges (top and left while pressed), the way a C64 picture faked a soft shadow. Nothing is blurred and there is no gradient. It is layered over the tile by a `Stack(fit: StackFit.expand)` (a Stack's default loose fit would let the tile collapse to its content), wrapped in `IgnorePointer` and a `RepaintBoundary`, so it takes no touches and repaints only when the tile is pressed or selected. It is not laid out: the tile keeps its size. A tile selected in the grid editor has its plain outline and gets the scanlines only. The effects sit over the tile's own content too, so text is under a faint scanline; that is intended, and the strengths were kept low for it.
- TILE EFFECTS ON / OFF (under FEEL in settings, default on) turns all of it off, for anyone who finds it busy or wants the plainest possible tiles; the thicker bevel stays either way. Not done, left as ideas: a raster-bar flicker, colour-clash blocks, and a per-theme strength (the beige and OLED themes use the same alphas).
- Phase 21's app icons come through `AppRepository.icon(packageName)` (PNG bytes or `null`), like every other piece of app access. `AndroidAppRepository` asks the Kotlin `AppsChannelHandler` (`getApplicationIcon`, drawn to a 144 px bitmap on the same worker thread as the app list, so an adaptive icon comes out already masked) and remembers the answer per app: one pending-or-finished `Future` per package, so a list scrolled back and forth or a tile drawn twice asks the platform once, an app with no icon is not cached (asked again next time), and at most 400 are kept, oldest dropped first with use moving an icon to the newest place. The Dart type is `AppIconLoader`; `TileServices.icons` carries it to the tiles (`main` passes `appRepository.icon`) and `AppDrawer.iconOf` to the rows. `AppIcon` shows the fallback (the first letter, in a frame on a drawer row, as a big glyph on a tile) until the bytes arrive and whenever APP ICONS is off in settings (FEEL, default on). An app tile puts the icon (at most 72 px, 90% of the room above the label) where the glyph was; a contact tile has no loader and stays a letter.
- The A–Z strip (`JumpIndex`) spreads its letters over the whole height it is given, at most 44 px a letter (fewer initials sit centred), instead of a fixed 20 px; taps and drags are mapped with the same offset. While a finger is on it each *new* letter gives the lightest tick (`Haptic.tick`, `selectionClick`, honouring the haptics setting) and the letters near the finger bulge out to the left (16 px) and grow (70%) with a cosine-squared falloff over four letters either side, following the finger as a fractional position and easing in over 110 ms and out over 220 ms. The letters are drawn outside the 24 px strip (`Clip.none`), over the list's right edge. A touch only counts as a tap on a letter after the press timeout (or once it becomes a drag), which is how the gesture arena works, so the wave starts a moment after a plain touch.
- Portrait only: `android:screenOrientation="portrait"` on the activity (so a rotation never starts) and `SystemChrome.setPreferredOrientations` at startup as a second line; `test/manifest_test.dart` guards the manifest attribute. `configChanges` still lists `orientation`, harmless with the lock.
- Phase 22's press rule, in `PressListener`. A touch is not a press until it proves it is one: the look (the bevel flip) comes on only when the finger has rested 90 ms without moving 8 px (`showAfter`, `visualSlop`), so a finger that lands and goes on to scroll never sinks a tile. It lets go the moment the finger moves past 8 px. A tap so quick that the look never came on still sinks for 90 ms *when it lets go* (`flashFor`), so it is seen to register: the press feedback moved from "finger down" to "the tap happened". The tick, and whether a release is a tap, use touch slop (18 px) and the long-press time, not the look. The 8 px and 90 ms sit under the tap recogniser's own slop and press timeout on purpose. `TileView` is stateless again and builds inside `PressListener`; the pointer stream can still outlive the tree, so `PressListener` guards `mounted` and cancels its three timers on dispose.
- The bar of keys along the top of home is two `BevelKey`s of equal width (SETTINGS left, + ADD TILE right), 44 px tall, in a fill a shade off the canvas (canvas mixed 22% toward the text colour, so it follows all three themes), a 2px lit and 4px shaded bevel (a little finer than a tile's 3 and 5) and the same press behaviour, replacing the two small text links. The grid starts 8px under them (its top padding is the gutter, not the margin), and there is no gap below the bar of its own.
- The A–Z strip's layout is now: the letters fill the middle 70% of the height (15% clear above and below), at most 44px a letter. A short strip (a sheet with the keyboard up) would make them tiny, so it takes more: not less than 14 px a letter (or, if even that will not fit, all of its height). While a finger is down the whole strip slides 30 px to the left, out from under it (the letters' resting position is by the edge of the screen, where the finger hides them), eased in over 110 ms and out over 220 ms, and the wave rides on top (swing cut to 12 px). A scrub now starts on the letter the finger landed on (`DragStartBehavior.down`, so a quick flick does not skip it), and `_reached` stops the tap-turned-drag from jumping and ticking twice on that letter; every new touch clears it.
- Phase 23's scrubber tweaks: the strip is 12 px wider than its 24 px column of letters (`edgeMargin`), so at rest the letters keep clear of the screen's edge while the touch area still reaches it; `pushOut` is 44 px and the wave is 22 px of swing, 100% growth over five letters either side (`waveReach`), plus a vertical spread (`waveSpread`, 6 px, a sine of the distance so it is nothing under the finger and at the reach's end, away from the finger on each side) and a lerp toward `TileColors.accent` by the wave's strength squared for the letter under the finger.
- Phase 24, reading mail. `MailService` gained `read(uid, {validity})` and `mark(uid, {read, validity})`, each with its own sealed result (`MailReadResult`: opened / gone / not set up / failed; `MailMarkResult`: marked / gone / not set up / failed), like `moveToTrash`. `read` first asks only for `UID FLAGS RFC822.SIZE` and refuses a message over 8 MB (`ImapMailService.maxReadBytes`) with a reason, rather than pulling a huge attachment down to look at a note; then fetches `ENVELOPE BODY.PEEK[]` (PEEK, so the fetch itself never sets `\Seen`) and only afterwards stores `\Seen` explicitly. That order is the point: a message that fails to open is left exactly as it was, and one that opens but whose marking fails is still shown, with `MailBody.markedRead` false so the sheet says so. Text is the plain part if there is one, else `plainTextFromHtml` of the HTML part (drops head, styles, scripts and comments; keeps paragraphs, breaks, list items and table rows as lines; decodes entities), tidied by `tidyMailText` (line ends, control and zero-width characters, blank-line runs) and cut at 20,000 characters at a word (`MailBody.truncated`); attachments are counted (`findContentInfo`), never shown. `CachedMailService` drops its kept listing on both calls, since unread counts change.
- The mail sheet has two modes. The list is as before, but a tap opens the message in a pane of its own (BACK, who/when/subject, the whole text in a `SelectableText` that scrolls, a note if it was cut or has attachments) and marks it read, as opening a mail does anywhere; the row behind turns read at once. At the foot of the pane: MARK AS UNREAD (MARK AS READ when it is unread, so it toggles) and TRASH, a `TileMetrics.margin * 2` apart so one is not hit for the other, TRASH still asking YES / NO first. The old expand-a-row-to-trash is gone; every action on a message is in the pane. `mark` and `moveToTrash` go by uid and the list's `validity`, so a renumbered inbox refuses both. A message gone from the server is dropped from the list and the sheet says so.
- The fake IMAP server (`test/fakes/fake_imap_server.dart`) now answers `UID FETCH` for `RFC822.SIZE` and `BODY.PEEK[]` (as a literal, so the real client library parses a real message), keeps a `seen` set that `UID STORE +/-FLAGS \Seen` changes and `STATUS UNSEEN` counts, and can be told to refuse a `\Seen` store. Messages can carry `text`, `html`, a whole `raw` message (attachments) or a lying `size`.
- The mail sheet's type sizes are 13 px for who and what, 12 px for the text of a message (line height 1.7), and 11 px for secondary lines, dates and buttons, up from 8 to 10: the pixel font is unforgiving small, and the reader is for reading. The widest rows (MARK AS UNREAD beside TRASH, and the MOVE TO TRASH? question with YES and NO) were checked to fit a 360 dp phone, and a test keeps them so.
- Phase 28 gave the alarm tile something real to show: `AlarmService` gained `next()` (`AlarmContent`/`AlarmTileSource`, a `TilePoller` at 1-minute intervals) alongside its existing `setTimer`/`setAlarm`/`showTimers`/`showAlarms`, rather than a parallel `AlarmRepository` — `MailService` already mixes a polled read (`latest`) with tap-only actions (`moveToTrash`, `setUp`) in one interface, so this follows that precedent instead of introducing a second alarm-shaped collaborator into `TileServices`. Kotlin's `AlarmChannelHandler` reused its existing channel for a `"next"` branch: `AlarmManager.getNextAlarmClock()?.triggerTime`, which needs no permission and is genuinely system-wide (the next alarm due from *any* app, the same one Android's own lock screen and status bar show), unlike everything else the handler does, which only ever acts on what this launcher itself asked for. There is no equivalent for a *timer* — Android exposes only the next alarm clock — so a timer stays write-only. The tile shows a dash (`--:--`), not a time, when none is set: a plausible-looking fixed "00:00" is exactly the bug this phase fixed. The tile also re-reads once its own sheet closes (`showAlarmSheet(...).then((_) => refreshNow())`), the same `TilePoller.refreshNow` pattern Text TV's viewer uses, so setting an alarm through this launcher shows up immediately rather than waiting up to a minute.
- Phase 27's font scaling (`FontScale` in `model/settings.dart`; small/normal/large/extra-large) is applied as one global `MediaQuery.textScaler` override in `app.dart`'s `MaterialApp.builder`, composed with — not replacing — whatever ambient scaler is already there (a small `_ScaledTextScaler` multiplies the ambient `scale(fontSize)` by the setting's factor). This reaches every ordinary `Text` widget for free (Flutter's default is to read the ambient scaler) and every manual `TextPainter` already written to read `MediaQuery.textScalerOf(context)` (`TvRow`'s fitting search for a Text TV page's fixed grid, `text_tv_tile_view.dart`'s headline painter), without a single call site touched. Composing rather than replacing was chosen over baking the factor into `tileLauncherTheme()`'s `TextTheme` specifically so the setting only ever adds to whatever text-size accessibility preference the phone's OS already provides, never overrides it — unlike the theme/dark-mode choice (which deliberately ignores the OS), losing a user's own OS-level accessibility text size would be a regression, not a design position. The settings screen's own live preview applies `TextScaler.linear(factor)` directly to a sample line rather than relying on the app-wide override, so it stays correct under a bare `MaterialApp` in tests too.
