# Tile Launcher — Plan

Goal: an Android home-screen launcher made of live tiles, so the user rarely has to leave it. The structure is a four-column mosaic of 1×1, 2×2, 4×2 and 4×4 tiles (see `design/mockups/`); the look is Commodore-era (see `design/reference/`): light blue on C64 blue, the sixteen VIC-II colours, hard edges, bevels instead of shadows.

Guidance for agents: [AGENTS.md](AGENTS.md) and [.agents/](.agents/README.md). Each step ends with `dart format`, `flutter analyze`, `flutter test` clean, `flutter build apk --debug` after touching `android/`, and — where it touches the phone — a device check. Small steps: finish and verify one before starting the next.

Phases 0–24 (foundation through the app itself being feature-complete: apps, mosaic, drawer, persistence, grid editor, clock, device tile, weather, agenda, people, mail, Text TV, calc/convert, alarms, settings, wallpaper, and several rounds of visual/UI polish) are done and archived in [.agents/archive/plan-phases-0-24.md](.agents/archive/plan-phases-0-24.md), along with their full changelog. This file now starts a fresh round of phases from the user's latest notes.

The sibling repo `../android_terminal_launcher` already solves some of these problems (weather, mail, calendar, contacts, Text TV) in pure-Dart services worth reading before inventing a solution here, but its presentation never transfers — there is no command line here.

## Next, in order

Each phase gets designed in detail only when it's reached; this is an outline so the order is agreed up front. Small, independent phases can be reordered without much cost — ask if a different order would be more useful before starting.

25. ~~**Grid editor: easier drag placement.**~~ **Done.** A held tile's target is split by its own diagonals into four triangles (left/right/top/bottom), so hovering near any edge of a tile shows an insertion marker on that side — a horizontal line above/below stacks the tile into another row, not just beside its target. Each tile's drop area now also reaches half a gutter's width past its own edges, meeting its neighbours halfway across the gutter, so the marker appears while crossing the gutter rather than only once fully over the next tile. `moveBeside`'s before/after model is unchanged; only which edge maps to which (and the marker's orientation) is new. 1247 tests total (+9), format/analyze clean; not yet checked on a phone.
26. ~~**Grid editor: more tile size options.**~~ **Done.** Four new sizes alongside the original small (1×1), medium (2×2), wide (4×2) and large (4×4): flat (2×1), tall (1×2), broad (3×2) and tower (2×4). `TileSize` gained a `fullWidth` flag (only `wide`/`large` set it) so `spanIn` scales a size to the full mosaic width or clamps it to its own column count, generically rather than by a per-case switch. The packer (`packTiles`) already worked for any span/row combination, so no changes there; the inspector's resize row became a `Wrap` so eight buttons don't overflow a phone-width panel. Serialisation (`PinnedTile.toJson`/`fromJson`, layout export/import) is already name-keyed off `TileSize.values`, so the new sizes needed no format change. 1251 tests total (+13), format/analyze clean; not yet checked on a phone.
27. ~~**Font scaling.**~~ **Done.** A FONT SIZE section in Settings (SMALL/NORMAL/LARGE/EXTRA LARGE, the same selection-box style as GAP BETWEEN TILES) with a live preview line. Applied as one `MediaQuery.textScaler` override in `app.dart`'s `MaterialApp.builder`, *composed* with whatever ambient scaler is already there rather than replacing it, so the setting only ever adds to — never removes — the phone's own OS-level accessibility text size. This reaches every ordinary `Text` widget for free, plus the couple of manual `TextPainter`s (`TvRow`, a Text TV page's own fixed 40-column grid; `text_tv_tile_view.dart`) that were already written to read the ambient scaler, without a single call site touched. Found in the process, out of scope here and tracked as #35: several tile content views (the clock among them) already overflow a one-row-tall tile (`TileSize.small`/`flat`) at a realistic phone width, independently of font scale — it reproduces at NORMAL too, so it predates both this phase and Phase 26. A follow-up fix (below the changelog note) corrected the mail tile specifically, found by the user testing on a phone: its wide inbox rows were fixed-height boxes sized off the bare type size, so EXTRA LARGE made a message's sender/subject paint taller than their row and bleed into the one below — a *cross*-axis overflow, which unlike the clock's *main*-axis one throws no exception, so it needed a geometric regression test, not `tester.takeException()`. 1261 tests total (+10), format/analyze clean; not yet checked on a phone.
28. ~~**Alarm tile fix.**~~ **Done.** The tile now shows the next alarm due (`AlarmManager.getNextAlarmClock()`, read with no permission — Android's one system-wide next alarm, set by whichever app's is soonest, not only ones set from here), or a dash (`--:--`) rather than a fake time when none is set. No equivalent exists for reading a timer, so that stays write-only. `AlarmService` gained `next()` alongside its existing set/open methods (mirroring `MailService`, which already mixes a polled read with tap-only actions in one interface, rather than a parallel `AlarmRepository`); a new `AlarmTileSource`/`AlarmContent` feed a `TilePoller` (1-minute interval), and the tile also re-reads immediately once the alarm sheet closes, not only on the next poll. Kotlin's `AlarmChannelHandler` gained one `"next"` branch reusing the existing channel. Not verified with `flutter build apk --debug`: no Android SDK is available in this session, and installing one is blocked by the environment's network policy (the gateway refuses `dl.google.com`); the Kotlin change was reviewed by hand against this repo's existing `getSystemService` idiom instead. 1262 tests total (+11), format/analyze clean; not yet checked on a phone.
29. ~~**Pane/sheet button spacing.**~~ **Done.** A `SizedBox(height: TileMetrics.gutter)` (8px) ahead of the top row in the four modal sheets whose button/tab row was the very first thing in the body with nothing but the sheet's own uniform `Padding(all: TileMetrics.margin)` above it: `alarm_sheet.dart` (TIMER/ALARM tabs + close), `calc_sheet.dart` (CALC/CONVERT tabs + close), `mail_sheet.dart` (BACK/REFRESH), `agenda_sheet.dart` (title + DAY/WEEK toggle). Out of scope, on purpose: `settings_screen.dart` and `text_tv_screen.dart` are full-screen routes whose top bar already sits behind a real `SafeArea(bottom: false)` (the actual status-bar inset) plus its own gutter, so their button row was never truly flush the way a modal sheet's was; and `contact_sheet.dart`, `contact_picker.dart`, `mail_setup_sheet.dart`, `add_tile_sheet.dart`, `quick_actions_sheet.dart` open on a title, a search field, or a list of full-width rows with their own generous padding, not a button row, so "flush against the top edge" didn't describe them. No new tests: purely an 8px spacing nicety, and the existing widget tests for all four sheets already re-ran clean, confirming nothing shifted or broke. 1277 tests total (unchanged), format/analyze clean; not yet checked on a phone.
30. ~~**Agenda: remember Day/Week and add week navigation and C[R]UD opertaions.**~~ **Done.** The DAY/WEEK tab is now a settings field (`agendaWeekView`, not offered on the settings screen — it's remembered state, not a preference — riding along in the same saved blob rather than a second store) so the sheet reopens on whichever was last chosen. A chevron row under the tab toggle steps a day or a week at a time in *both* Day and Week view (decided in Day's favour: cheap to add, and "what's tomorrow look like" is a reasonable thing to want without switching to Week), with a heading — TODAY/TOMORROW/YESTERDAY or THIS WEEK/NEXT WEEK/LAST WEEK, else a formatted date or range — between them; the navigated offset itself resets on reopen, only the tab choice persists. Tapping an event now opens a new read-only detail sheet (`event_detail_sheet.dart`) — when, where, and the event's own description (a new field: `CalendarEvent.description`, read from Android's calendar provider alongside the existing columns) — each in a bordered "field" box so a later phase can turn it into an edit form (the box becoming a `TextField`'s own border) without a rewrite; create, update and delete are not built yet, only this read. 1296 tests total (+18), format/analyze clean; debug APK builds; verified by the user on their phone.
31. ~~**Device tile: icons and more metrics.**~~ **Done.** Not the two generated mockups as-is: full colour, gradients and a drop shadow, all against this app's own flat/VIC-II-only rule (`AGENTS.md` #5) — the same call already made about `design/mockups/`'s Fluent references. Not a Flutter icon-package either: this app already has its own way of drawing a small in-app icon in code with no asset ([WeatherIcon]'s sky pictures), and a generic icon font would look like a different app glued onto this one. Extracted that painter into a shared `PixelIcon` (`ui/pixel_icon.dart`, `WeatherIcon` now built on it too, nothing else changed) so new icons don't each carry their own copy, then built `BatteryIcon` (its charge level filled bottom-up — continuous, not a discrete empty/half/full bitmap set — `null` draws the outline only), `DiskIcon` and `MemoryIcon` (`ui/device_icons.dart`) on an 8x8 grid rather than `WeatherIcon`'s 12: coarser blocks read better at the small size a meter row has room for than the same detail shrunk past legibility. For "more metrics", added one rather than a whole selector UI: free RAM (`ActivityManager.getMemoryInfo`, as cheap and permission-free as the existing battery/storage reads), a third meter row beside the existing two — a selector felt like solving a problem three meters don't yet have. Not independently confirmed by the model itself: two different in-editor render-to-PNG approaches to preview the icons both proved unreliable (a paint-time `Transform.scale` samples only whatever sits at the tiny box's centre; a corrected `pixelRatio`-based capture rendered a puzzling, seemingly stale result under time pressure), so this shipped on the design reasoning above rather than a confirmed look — worth a deliberate look on the phone, not just a glance in passing. 1308 tests total (+27, including the `PixelIcon` extraction's `WeatherIcon` regression coverage re-running clean), format/analyze clean, debug APK builds.
32. ~~**Explore other Google-service tiles.**~~ **Done.** Findings and conclusion recorded in [.agents/google-services-survey.md](.agents/google-services-survey.md), linked from the guide index. Short version: calendar and contacts already surface a synced Google account's data (they read Android's own providers, not a Google API), so there's nothing to add there; every genuine Google *cloud* API (Gmail, Tasks, Drive, Photos, YouTube) needs an OAuth sign-in and a reviewed Google Cloud project this app has avoided everywhere else, for value already covered another way in each case — recommended skip. The one real opening is Health Connect (steps/activity), an on-device API with no sign-in that fits this app's existing tile architecture exactly — left off this list on purpose, since wanting a steps tile is a new feature decision, not one already implied by what's on the home screen; add it as its own phase if wanted.
33. ~~**File/disk explorer.**~~ **Done.** A new FILES tile opens a sheet that works the way Android's own Files app does: "all files access" granted once (`android.permission.MANAGE_EXTERNAL_STORAGE`, requested via `package:permission_handler`, a well-established, actively-maintained plugin for this fiddly Settings-redirect special permission), then every storage volume on the phone — INTERNAL STORAGE, an SD card, … — is browsable and deletable as an ordinary file tree, ordinary `dart:io` doing the reading and deleting once access is granted (no document-tree API needed at all). The one thing `dart:io` cannot do — ask Android what storage volumes even exist — is a small hand-rolled Kotlin channel (`FilesChannelHandler`, `"storageRoots"`), not a package: a first pass used `package:external_path` for this, but Flutter warned it still applies the Kotlin Gradle Plugin the old way (future versions will refuse to build it), so it was replaced with the same few lines of native code this app already writes for everything else. This replaced the first version of this phase, which picked one folder at a time through Storage Access Framework (`package:saf_util`) — worth having tried, since it needed less permission, but not what was actually wanted once asked directly. Folders first, files biggest first, each deletable behind a YES/NO confirmation except a volume itself; a long filename shortens in the middle with its extension kept, measured against the real `TextStyle` with `TextPainter`; new `FolderIcon`/`DocumentIcon`/`TrashIcon` join `PixelIcon`'s device-tile icons. 1354 tests total, format/analyze clean, debug APK builds (`compileSdk` bumped to 37 for `permission_handler_android`); verified by the user on their own phone across several rounds, including one real bug this model introduced and initially missed: a stale scoped `flutter analyze`/`test` (individual files, not the whole repo) let a leftover `AndroidFilesService(store: store)` call in `main.dart` survive a constructor rewrite uncaught, only surfacing as a compile error on the user's own `flutter run` — full-repo checks before calling work done from now on, not just the files just touched.
34. ~~**Settings page visual grouping.**~~ **Done.** Each settings section is now a bordered box (the same `Border.all(color: TileColors.bezel, width: TileMetrics.bevel)` a tile itself draws, reused rather than inventing a second boxed look), with a small accent-coloured tick beside its heading instead of a bare underline, and doubled top spacing between one box and the next — a group now reads as one unit at a glance instead of a heading plus a thin rule. No new tests (purely visual restructuring of `_Section`; the existing 1354 tests, none of which assert `_Section`'s internal structure, all re-ran clean).
35. ~~**More tile sizes.**~~ **Done.** Every 1–4 column by 1–6 row combination now exists (24 sizes total, up from 8): the original small/flat/tall/medium/broad/wide/tower/large kept their names (so an already-saved layout still reads back the same shape), and the 16 new shapes were added under a systematic `sizeCxR` name rather than inventing a word for each — the resize picker in `tile_inspector.dart` already labels every button from its plain `columns`x`rows` numbers, never the enum name, so nothing there needed touching. The packer (`packTiles`) is a generic skyline algorithm already indifferent to how many rows a tile is, so it needed no change either. Two of the new sizes (`size3x1`, `size4x1`) are one row tall, the same footprint `small`/`flat` already are — which resurfaced the plan's own long-standing open question below ("short-tile content overflow"): `test/app_test.dart` used to simply exclude `small`/`flat` from its one-of-every-size coverage rather than fix the clock tile's overflow there, and the two new sizes would have hit the exact same bug. Answered this time instead of sidestepped again, and for every tile kind, not just the clock: a new `_oneOfEachKindAndSize` check (all 13 kinds × all 24 sizes, at EXTRA LARGE) found the same "a wide tile is no taller than a narrow one" mistake in eight of the thirteen content views (clock, state, alarm, calc, device, weather, agenda, mail — files and Text TV had already been through this once each in earlier phases and still had one unguarded fallback state apiece). Every one now shrinks instead of overflowing: an outer `FittedBox` around the whole stack (the pattern the files tile already used) for the ones with fixed content, plus a `Flexible` around the specific element that used to assume unbounded height (clock's time, state's state-word) for the two with one optional line worth dropping first. The device tile's three meters needed one extra wrinkle: `CrossAxisAlignment.stretch` cannot stretch to the unbounded width a bare `FittedBox` gives its child, so it sits in a `SizedBox` pinned to the tile's real width first. 1364 tests total (+10: `tile_size_test.dart` locking in the full size matrix and `fullWidth` still only applying to `wide`/`large`; the new every-kind-every-size check; three clock-tile regression tests for one row tall, taller, and EXTRA LARGE at one row), format/analyze clean.
36. ~~**Bluetooth tile.**~~ **Done.** The dual-functionality question ("toggle vs. open a pane") resolved the same way the alarm tile already answers it: the tile itself only ever opens a sheet (`bluetooth_sheet.dart`, a `StateTileContentView` glancing at `[ON]`/`[OFF]`/`N/A`, matching soundMode/flashlight), and both the toggle and the paired-device list live inside that sheet. What the sheet's TURN ON/OFF button actually does had to change from the first plan, though: Android's `Settings.Panel` (a quick, in-place system overlay this app hoped to reuse, the way it works for wifi/NFC/volume/internet) turns out to have no Bluetooth entry at all — a real compile error (`Unresolved reference 'ACTION_BLUETOOTH'`) caught this before it shipped. The actual asymmetry Android allows: off, `BluetoothAdapter.ACTION_REQUEST_ENABLE` shows a quick system confirm dialog without leaving the app; on, there is no equivalent "request disable" dialog, so it falls through to the full `Settings.ACTION_BLUETOOTH_SETTINGS` screen instead, the same one MANAGE DEVICES and tapping a paired device both open — connecting or disconnecting a specific device has no public API for a third-party app either (only reading its per-profile connection state does, `BluetoothManager.getConnectionState`), so a device row is a status line, not a button that pretends to act. `BLUETOOTH_CONNECT` (Android 12+) is asked for through the same generic `AppPermission`/`PermissionsChannelHandler` calendar/contacts/phone/sms already use, not a special case; `BLUETOOTH` alone (a normal, install-time permission) covers it below that. 1386 tests total (+22), format/analyze clean, debug APK builds; not yet checked on a phone — Bluetooth hardware can't be exercised on this session's emulator or without one, so this needs the user's own device to actually confirm the enable dialog, the paired-device list and their connection states look and behave right.
37. ~~**Tile size overhaul selector.**~~ **Done.** Went with the second suggestion, the one leaned toward — an Excel-"insert table"-style grid, not the two-buttons-per-size idea: `TileSizeGridPicker` (`ui/tile_size_grid_picker.dart`) is a fixed 4-column-by-6-row grid of cells; tapping or dragging toward one paints (and, on release, picks) every size from 1×1 up to that cell's own shape — the rectangle from the top-left corner to wherever the finger is, "like Tetris blocks" but painting rather than dropping. `TileSize` gained one lookup, `TileSize.of(columns, rows)`, to turn a painted cell back into the matching enum value (every combination has exactly one, Phase 35's whole premise). The FLIP button answers the orientation half of the first suggestion without needing it as a whole separate mode: it swaps the *current* selection's columns and rows (3×2 to 2×3) rather than halving 24 visible options into 12, since the grid itself already shows every option at a glance — disabled once a tile is taller than 4 rows, since a size with more than 4 columns doesn't exist to flip into. The answer to "did we already implement no-overflow-on-shrink": yes, Phase 35, and this phase didn't need to touch any tile content view — only the picker that chooses a size, never what a size renders as. The proportional "preview of the actual tile" idea narrowed to the painted rectangle's own aspect ratio (the cells filling in as the finger moves) rather than rendering the tile's real content at scale, which would have meant either duplicating every tile view in miniature or actually mounting one live — judged not worth it for a picker whose own shape already reads as the preview. 1395 tests total (+31: the grid picker's own widget tests, `TileSize.of`'s model tests, and the FLIP/resize integration tests in `home_shell_test.dart` rewritten for the new grid instead of the retired size buttons), format/analyze clean.
38. ~~**Emphasize C64 style.**~~ **Done.** Only two constants files changed, no new widgets: `TileMetrics.tileBevelLight`/`tileBevelDark` (the tile bevel border widths) went from 3/5 to 4/6 — broader, and still exactly one `TileMetrics.bevel` (2) apart, the designed relationship `tile_press_test.dart` already checks (a pressed tile sinks its content by exactly that difference) and now `tile_gloss_test.dart` checks directly too, so a future tweak breaks there with a clear reason instead of a bare offset mismatch. `TileGlossPainter`'s scanlines went closer-set and more visible (every 4px at 5% opacity to every 3px at 9%) and the shine thicker and brighter (2px at 32% to 3px at 42%); the dithered shade nudged up alongside it (20% to 24%, not asked for by name but left proportionally behind otherwise). Tuned by feel against the stated "tastefully, not overboard" brief, not a formula — genuinely worth the user's own look on a phone before calling the balance right. 1396 tests total (+1: the new bevel-invariant test), format/analyze clean.
39. ~~**Emails: bulk delete.**~~ **Done.** SELECT (beside REFRESH, disabled with nothing to select) turns the list into checkboxes — each a small bordered square in the same flat, no-glyph style the size grid picker's own cells use, not a platform checkbox that would look borrowed — and the header itself becomes "N SELECTED" with CANCEL and DELETE (N), DELETE disabled at zero. DELETE asks first (the list's own version of a single message's TRASH confirm), then moves each selected message one at a time through the existing `moveToTrash` (no new bulk method on `MailService` — nothing here needs the server to do more than one message at a time, only this screen to ask for several), showing "DELETING x of y..." as it goes, which is the progress indicator asked for without inventing a fake determinate one where the real number already exists. Once done, it reloads from the server rather than trusting the local list edits alone — "automatically refresh," taken literally, and a real difference from the single-message TRASH flow (which only ever edits the local list, never reloads) since bulk delete was explicitly asked to. 1403 tests total (+7), format/analyze clean.

## Deliberately different from the terminal launcher

- **No command line.** `help`, `ui rich|plain`, aliases, `&&` chaining and macros have no counterpart here; a tile is either self-evident or badly designed.
- **`list`, `open`, `refresh`, `uninstall`** stop being commands and become the drawer, a tap, a pull-to-refresh and a long-press action.
- **A small set of canvases**, not six themes. The sixteen VIC-II colours are the palette in all of them; the canvas changes, not the tile colours.
- **Rich vs. plain** does not exist. Every tile is a card by definition.

## Not implemented (on purpose or not yet)

- **Widgets**: hosting real Android `AppWidget`s is a much larger job (`AppWidgetHost`, permissions, remote views) and is not planned. Tiles are ours.
- **Notification badges** need notification-listener access, which is a heavy permission; only the counts we can get another way (mail, calendar) are planned.
- **Wallpaper pass-through, acrylic blur, 3D tile tilt, rounded corners**: all in the Stitch mockups, none in this design. Flat, opaque, square.
- **Landscape and tablets**: portrait phone only until the phone version is good.
