# Tile Launcher — Plan

Goal: an Android home-screen launcher made of live tiles, so the user rarely has to leave it. The structure is a four-column mosaic of 1×1, 2×2, 4×2 and 4×4 tiles (see `design/mockups/`); the look is Commodore-era (see `design/reference/`): light blue on C64 blue, the sixteen VIC-II colours, hard edges, bevels instead of shadows.

Guidance for agents: [AGENTS.md](AGENTS.md) and [.agents/](.agents/README.md). Each step ends with `dart format`, `flutter analyze`, `flutter test` clean, `flutter build apk --debug` after touching `android/`, and — where it touches the phone — a device check. Small steps: finish and verify one before starting the next.

## Next, in order

Each phase gets designed in detail only when it's reached; this is an outline so the order is agreed up front. Small, independent phases can be reordered without much cost — ask if a different order would be more useful before starting.

The user's next batch, agreed 2026-09-30 (tested only once every phase below is in, per the user's own instruction — not phone-tested phase by phase):

60. **Mail reader: To/Cc chips + Reply All.** `MailBody` gains `to`/`cc` participant lists from the envelope; the reader shows them in the same bordered chip look the From address already uses, each tappable to compose to that address. A REPLY ALL button beside REPLY when there is more than one distinct recipient (To+Cc minus the account's own address).
61. **Mail reader: attachments + Show images.** Attachment name/size/bytes and an images-resolved HTML variant, both free from the message already fetched by `read()` (no extra network). A DOWNLOAD button per attachment (new Kotlin MediaStore channel, straight to the Downloads folder, no permission prompt) and a SHOW IMAGES button that reveals inline/remote pictures on demand (stays stripped until tapped).
62. **Compose: multi-recipient To/Cc chips.** To and Cc fields that hold several addresses: a complete address followed by a delimiter becomes a chip; backspacing on an empty field un-chips the last one back to text. `MailService.send` takes multiple To and a Cc list.
63. **Compose extras.** Contact autocomplete in To/Cc (from the existing `ContactsRepository`), a SELECT ALL for mail's bulk-select mode, and a signature setting auto-appended to new/reply/forward messages.
64. **Mail search/filter.** A FILTER pane (free text over subject+body, From, To, a date range or "older than" N days/weeks/months/years) via server-side IMAP SEARCH; applied filters show as removable chips above the list.
65. **Calendar: persist Week:Grid zoom.** The pinch-zoom level resets between weeks because `AgendaWeekGrid`'s state is torn down while the sheet shows `SizedBox.shrink()` during a reload; move it into `LauncherSettings` as remembered UI state.
66. **Calendar: sheet close button.** An "X" at the top of the agenda sheet, the same `PadKey` convention every other sheet already uses.
67. **QR scanner tile.** A dedicated, C64-styled full-screen scanner (camera + on-device decode, a new dependency), OPEN/COPY on a successful decode. No camera tile — the user pins the phone's own Camera app from the drawer instead.

Note: this session's container has no Android SDK and downloading one is blocked by the network policy (`dl.google.com` denied), so `flutter build apk --debug` cannot be run here for phases 61 and 67, which touch `android/`; `dart format`/`flutter analyze`/`flutter test` still gate every phase, and the user should build/install the APK themselves before testing on the phone.

## Deliberately different from the terminal launcher

- **No command line.** `help`, `ui rich|plain`, aliases, `&&` chaining and macros have no    counterpart here; a tile is either self-evident or badly designed.
- **`list`, `open`, `refresh`, `uninstall`** stop being commands and become the drawer, a tap, a pull-to-refresh and a long-press action.
- **A small set of canvases**, not six themes. The sixteen VIC-II colours are the palette in all of them; the canvas changes, not the tile colours.
- **Rich vs. plain** does not exist. Every tile is a card by definition.

## Not implemented (on purpose or not yet)

- **Widgets**: hosting real Android `AppWidget`s is a much larger job (`AppWidgetHost`, permissions, remote views) and is not planned. Tiles are ours.
- **Notification badges** need notification-listener access, which is a heavy permission; only the counts we can get another way (mail, calendar) are planned.
- **Wallpaper pass-through, acrylic blur, 3D tile tilt, rounded corners**: all in the Stitch mockups, none in this design. Flat, opaque, square.
- **Landscape and tablets**: portrait phone only until the phone version is good.
